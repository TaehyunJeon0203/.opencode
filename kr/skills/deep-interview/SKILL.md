# Deep Interview

모호한 요청을 즉시 구현하지 말고 실행 가능한 요구사항으로 먼저 정리한다.

한 번에 질문 하나만 한다. 구현 범위·위험·완료 기준을 가장 크게 바꿀 불확실성부터 해결한다. 코드베이스를 확인하면 알 수 있는 내용은 사용자에게 묻지 않는다.

## 질문 축

가장 불명확한 축을 다음 순서로 고른다.

1. 목표
2. 범위와 제외 범위
3. 제약
4. 완료 기준
5. 기존 맥락과 영향 범위

## 인터뷰 규칙

- 모호성이 구현·범위·위험·인수 기준을 실질적으로 바꿀 때만 질문한다.
- 각 질문 전에 현재 이해를 간결하게 요약한다.
- 막힌 결정을 명시한다.
- 결정이 필요한 질문에는 항상 구체적인 선택지 2~3개를 제시한다.
- 마지막 선택지는 항상 `- (기타: 직접 입력)`으로 둔다.
- 유용할 때 에이전트 추천을 `(권장: 짧은 이유)`로 표시한다. 추천은 안내일 뿐 확정이 아니다.
- 전략·예산·보안·외부 공개·운영 영향·되돌리기 어려운 결정에는 추천하지 않는다.
- 예시가 사용자의 의도를 부당하게 좁힐 수 있어도 직접 입력 선택지는 반드시 제공한다.
- 질문은 간결하게 한다. 이유 설명은 필요할 때만 한 문장으로 덧붙인다.
- 답변을 다음 질문의 현재 이해에 반영한다.
- 요구사항을 임의로 만들어내지 않는다.

## 질문 형식

```text
현재 이해: {요청과 지금까지 결정된 내용의 간결한 요약}
막힌 결정: {가장 중요한 미해결 결정}
질문: {질문 하나}
선택지:
- A. {선택지} (권장: {짧은 이유})
- B. {선택지}
- (기타: 직접 입력)
```

안전한 추천이 없으면 추천 표시를 생략한다. 질문마다 미해결 결정은 하나만 둔다.

## 종료 기준

다음 내용이 명확해지면 인터뷰를 종료한다.

- 목표
- 포함·제외 범위
- 제약
- 완료·인수 기준
- 남은 열린 질문

마지막에는 전체 대화록 대신 결정사항과 열린 질문만 요약한다. 남은 결정이 결과를 크게 바꿀 수 있으면 구현 전에 확인을 받는다.
